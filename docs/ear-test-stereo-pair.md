# 人耳判定：AirPlay 2 推到 L16A 时，卧室「立体声组合」整组响应

**结论：整组响应，且左右声道分离正常。**

这条结论回答的是 `research/lan/lan-paths.md` §10 ① 留下的、**只能靠耳朵**回答的分叉问题：
局域网里**只有 L16A（`Xiaomi Sound-左` / `192.168.1.21`）广播 AirPlay**，那么把音频推给它时，
是整组一起响，还是只有左箱响？

## 判定方法

用 [`tools/airplay_ear_test.py`](../tools/airplay_ear_test.py) 推一段**左右交替**信号：

* 440 Hz 正弦，**每 1.2 秒在左声道 / 右声道之间跳一次**，共 12 秒；
* 音高始终不变 —— 所以「跳不跳」只可能来自**声道位置**，排除了音高带来的干扰；
* 振幅 **0.85 FS（−1.4 dBFS）**，AirPlay 音量 **70**，两只音箱硬件音量先统一设为 **55**
  （`mediaplayer.player_set_volume {"volume":55,"media":"app_ios"}`）。

> 音量为什么是重点：`research/lan/probe_airplay2_stream.py` 生成的测试音振幅只有
> **0.12 FS（−18.4 dBFS）**，即使把 AirPlay 音量拉到 80，用户反馈仍然是「太轻了 / 听不清」。
> 换成本工具的 0.85 FS 之后才具备可判定的响度。**后续所有需要人耳的测试都应当用 ≥0.7 FS。**

## 结果

用户答：**「声音在左右两边跳来跳去」**。

| 观察到的现象 | 含义 |
|---|---|
| 声音在左右两边跳 | **两只音箱都在响**，且左右声道被正确分发到左/右箱 |

即：

* L16A 收到 AirPlay 2 流之后，**把右声道转发给了 L16B**（`Xiaomi Sound` / `192.168.1.171`）；
* 立体声组合在 AirPlay 路径上是**作为一个整体**工作的，不需要分别给两只推流；
* 因此**卧室这套不需要 `192.168.1.171` 的独立通路**（`lan-paths.md` §10 ⑤「B 机只有 miIO 与
  `_mi-connect` 两条路」这个问题，对卧室场景**不再是阻塞项**）。

## 对架构的影响

| 目标 | 通路 | 端到端延迟 | 依赖小米云 | 依赖小米账号 |
|---|---|---|---|---|
| **卧室立体声组合（L16A+L16B）** | **原生 AirPlay 2 直推 `192.168.1.21:7000`** | **~300 ms**（声明窗口下限 250 ms） | **否** | **否** |
| 其它单只音箱（如 L05C） | 小米云 `player_play_url` + 音箱回拉本机 HTTP 流 | 1~2 s | 是 | 是 |

这正是用户「延迟太高了」这条诉求的解法：**卧室这套走 AirPlay 2，延迟降一个数量级，且完全绕开小米云。**

## 尚未验证 / 遗留

1. **声学延迟仍未实测**：本机麦克风在本轮所有实验中都是数字静音（`lan-paths.md` §3.4e），
   因此 ~300 ms 是**协议声明值 + 机制推算**，不是实测值。要实测需要一只可用的麦克风。
2. **L05C（`小爱音箱Play增强版`）没有任何本地通路**，只能走云。
3. 立体声组合的**主从角色**在云端不暴露（`mixplay-pc-audio/scout/findings.md`），
   本结论说明「主」是 L16A —— 但这只对 AirPlay 路径成立。
